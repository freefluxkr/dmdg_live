12-3. Kanban Multi-Agent 협업

⚠️ 부분 검증: 아래 내용은 v0.16.0 소스 코드(tools/kanban_tools.py, hermes_cli/kanban.py·kanban_db.py·kanban_specify.py·kanban_decompose.py·kanban_diagnostics.py)를 분석한 결과입니다. 카드 상태는 v0.16.0 기준 9가지이며, 본문은 핵심 흐름만 다룹니다. 실제 운영 테스트는 아직 진행하지 않았습니다.

같은 머신에서 여러 Hermes 에이전트가 협업하는 구조가 v0.14.0에서 본격적으로 도입됐습니다. 한 프로필이 작업을 잘게 쪼개 보드에 올리면, 다른 프로필이 그 작업을 가져가 처리하고, 또 다른 프로필이 결과를 평가·전달합니다. 보드가 동기화 지점 역할을 하므로, 에이전트끼리 직접 공유해야 하는 컨텍스트가 줄어듭니다.

전체 흐름

flowchart TD
    A["오케스트레이터\n(specify로 분해)"] -- "todo / ready" --> B["Kanban 보드\n(SQLite 영속화)"]
    B -- "claim" --> C["워커 #1\n(도구 실행)"]
    B -- "claim" --> D["워커 #N\n(도구 실행)"]
    C -- "done" --> E["Notifier\n(메시지·이벤트 발송)"]
    D -- "done" --> E

세 역할은 모두 일반 Hermes 에이전트입니다. 다만 config.yaml의 프로필 설정에 따라 사용하는 도구와 모델만 다릅니다. 보드는 SQLite에 저장되므로, 어느 한 프로필의 실행이 중단돼도 다른 프로필이 이어받을 수 있습니다.

카드 상태 흐름

카드는 다음 상태를 거칩니다.

v0.16.0 기준 카드 상태는 triage·todo·scheduled·ready·running·blocked·review·done·archived 9가지입니다. 핵심 흐름은 다음과 같습니다.

flowchart LR
    triage --> todo --> ready --> running --> done
    running -- "검토 요청" --> review --> running
    running -- "블로커 발생" --> blocked -- "해제" --> running
    ready -- "오래 머무름" --> stranded_in_ready
상태 의미
triage 러프한 아이디어(보통 제목만) 상태. specify/decompose가 사양을 채워 todo로 승격
todo 사양이 확정돼 의존 카드 완료를 기다리는 상태. 의존이 없으면 곧 ready로 승격
ready 워커가 가져갈 수 있는 상태. 의존 카드가 모두 done(또는 archived)이 되면 자동 승격
running 워커가 클레임한 상태. 클레임은 기본 약 15분간 유효하며 heartbeat로 갱신됩니다. 갱신 없이 만료되면 다음 디스패처 틱이 회수하고, 대시보드는 reclaim·reassign을 권고합니다
blocked kanban_block으로 표시한 상태. kanban_unblock(오케스트레이터 전용)으로 풀림
review 워커가 사람 검토를 요청하며 옮긴 상태. 검토자가 다시 running으로 클레임
done 워커가 kanban_complete로 마친 상태
stranded_in_ready 진단상 상태. 워커가 오랜 시간 클레임하지 않은 ready 카드

상태 전이는 모두 SQLite 트랜잭션으로 처리되며, 두 워커가 같은 카드를 동시에 잡으려 해도 한쪽만 성공합니다(아래 「안전장치」 참고).

주요 도구

오케스트레이터·워커가 호출하는 도구는 tools/kanban_tools.py에 모여 있습니다.

도구 역할
kanban_create 새 작업 카드 생성. 의존(parents)이 있으면 todo, 없으면 ready로 승격. triage=True면 triage로 진입
kanban_list 보드 상태별·소유자별 카드 조회 (오케스트레이터 전용)
kanban_show 단일 카드 상세 조회
kanban_complete 완료 처리 (run id로 소유권 검증)
kanban_block 블로커 등록·블록 사유 기록
kanban_unblock 블로커 해제 (오케스트레이터 전용)
kanban_heartbeat 워커가 살아 있음을 보드에 통지
kanban_comment 카드에 코멘트 추가
kanban_link 카드 간 의존 관계 등록

specify — 작업 분해 보조 LLM

오케스트레이터가 큰 목표를 받으면 보조 LLM이 그 목표를 보드에 올릴 만한 단위로 쪼개 줍니다. specify(hermes_cli/kanban_specify.py)는 카드 하나의 사양을 다듬어 triage에서 todo로 올리고, 여러 카드로 펼치는 그래프 분해는 hermes kanban decompose(hermes_cli/kanban_decompose.py)가 맡습니다. 보조 LLM이 작업 분해와 우선순위 결정을 맡으므로, 주 모델의 컨텍스트 부담이 줄어듭니다.

안전장치

여러 프로필이 같은 보드를 함께 사용하므로, v0.14 소스 코드에는 동시성과 복구 상황에 대비한 안전장치가 다음과 같이 들어 있습니다. 실제 운영 테스트는 후속 작업으로 진행 예정입니다.

  • 원자적 클레임(atomic claim): 카드를 ready에서 running으로 옮길 때 단일 SQLite 트랜잭션으로 처리합니다. 코드상 두 워커가 같은 카드를 동시에 잡으려 해도 한쪽만 성공하고, 다른 쪽은 즉시 실패하도록 작성돼 있습니다.
  • stranded_in_ready 진단: hermes_cli/kanban_diagnostics.py가 ready 상태로 오래 머무는 카드를 감지합니다. 워커가 중단됐거나 heartbeat를 보내지 못한 채 멈춘 카드를 표시하므로, 오케스트레이터가 해당 카드를 회수하거나 다시 할당할 수 있습니다.
  • notifier rewind: 메시지를 보낸 뒤 응답을 받지 못해 재시도할 때, notifier가 같은 메시지를 두 번 보내지 않도록 보드의 마지막 성공 시점으로 되돌아갑니다.
  • kanban_comment author 검증 강화: 코멘트 작성자를 프로필 식별자에서 직접 가져오도록 작성돼, 다른 워커 이름으로 코멘트를 남기는 우회 경로를 차단합니다.

언제 쓰면 좋은가

  • 작업이 독립 조각으로 잘 쪼개지는 경우: 코드 변경 N개, 페이지 N개 정정, 외부 호출 N건 같은 패턴
  • 다른 모델·도구를 섞고 싶을 때: 오케스트레이터에는 추론에 강한 모델을, 워커에는 빠르고 저렴한 모델을 두어 비용과 속도의 균형을 맞춥니다.
  • 무인 운영: /goal과 결합해 모든 카드가 완료될 때까지 자동으로 진행합니다.
  • 사람-에이전트 혼합: 사람이 카드를 추가하고 에이전트가 처리, 또는 그 반대

반대로 단일 작업·짧은 대화·실시간 사람 입력 중심의 흐름에서는 보드를 관리하는 부담이 더 큽니다. 이런 경우에는 일반적인 단일 세션으로 끝내는 편이 자연스럽습니다.

실전 사례는 13장에서

13장의 실전 프로젝트(코드 분석·뉴스 브리핑·팀 봇 등) 중 작업이 충분히 잘게 나뉘는 경우는 Kanban Multi-Agent 구성으로 옮길 수 있습니다. 13장에서는 실제 보드 운영 예시와 모델 슬롯 배분 방식을 다룹니다.
