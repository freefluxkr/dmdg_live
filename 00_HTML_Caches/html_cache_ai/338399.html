11.1 Zero-Shot 프롬프팅 — 예시 없이 지시하기

Zero-Shot 프롬프팅(Zero-Shot Prompting)은 AI에게 아무런 예시를 주지 않고 작업을 지시하는 가장 기본적인 방식입니다. "제로(0)샷"이란 말 그대로 예시가 0개라는 뜻입니다.

현대의 대형 언어 모델(LLM)은 방대한 데이터로 사전 학습되어 있기 때문에, 많은 일반적인 작업에서 예시 없이도 상당히 좋은 결과를 냅니다.

Zero-Shot의 기본 구조

[작업 설명] + [입력 데이터]

예시, 단계 설명, 추가 힌트 없이 오직 무엇을 해야 하는지만 알려줍니다.

실전 프롬프트 예시

문장: "오늘 날씨가 정말 좋네요."

예시 2 — 번역

다음 한국어 문장을 영어로 번역해 주세요.

문장: "인공지능은 우리의 일상을 바꾸고 있습니다."

[기사 내용 붙여넣기]

Zero-Shot의 장단점

구분 내용
장점 빠르고 간편함, 예시 준비 불필요
장점 간단한 작업에서 충분히 좋은 결과
단점 복잡하거나 형식이 중요한 작업에서는 결과가 불안정함
단점 AI가 원하는 방향을 정확히 파악하지 못할 수 있음

Zero-Shot은 "일단 해보기"에 적합합니다. 결과가 만족스럽지 않을 때 Few-Shot이나 CoT로 업그레이드하세요.

11.2 Few-Shot 프롬프팅

Few-Shot 프롬프팅(Few-Shot Prompting)은 AI에게 작업 예시를 몇 개 제공하여 원하는 형식과 패턴을 학습시키는 기법입니다. "몇(Few)번의 샷(Shot)"처럼 몇 가지 예시를 보여주는 방식입니다.

One-Shot vs Few-Shot

구분 예시 개수 특징
Zero-Shot 0개 예시 없음, 빠르지만 불안정
One-Shot 1개 예시 1개, 기본 방향 제시
Few-Shot 2~5개 예시 여러 개, 패턴 명확화

일반적으로 예시는 3~5개가 가장 효과적입니다. 너무 많으면 프롬프트가 길어지고, 너무 적으면 패턴 파악이 어렵습니다.

예시 선택 전략

좋은 Few-Shot 예시를 고르는 기준은 다음과 같습니다.

  • 다양성: 다양한 케이스를 포함하여 AI가 여러 상황을 파악하게 합니다.
  • 명확성: 입력과 출력이 명확하게 대응되어야 합니다.
  • 일관성: 모든 예시가 동일한 형식을 따라야 합니다.
  • 대표성: 실제 입력과 유사한 예시를 선택합니다.

11.3 Chain-of-Thought (CoT) 프롬프팅

Chain-of-Thought(CoT) 프롬프팅은 AI가 최종 답을 바로 내놓는 대신, 단계별 사고 과정을 거쳐 답에 도달하도록 유도하는 기법입니다. 사람이 복잡한 문제를 풀 때 "먼저 이것을 계산하고, 다음에 저것을 고려하고..." 하는 방식과 같습니다.

"단계별로 생각해 봐(Let's think step by step)"라는 한 마디가 AI의 정확도를 크게 높입니다.

Zero-Shot CoT vs Few-Shot CoT

Zero-Shot CoT는 예시 없이 "단계별로 생각하라"고만 지시합니다.

Few-Shot CoT는 단계별 사고 과정이 담긴 예시를 함께 제공합니다.

구분 예시 유무 특징
Zero-Shot CoT 없음 빠르게 적용 가능, "단계별로 생각해봐" 한 줄 추가
Few-Shot CoT 있음 더 정확하고 안정적, 예시 준비 필요

Zero-Shot CoT 예시

사과가 15개 있습니다. 3명이 똑같이 나눠 가지면 한 사람당 몇 개를 가지게 될까요?

단계별로 생각해 보세요.

AI가 "15 ÷ 3 = 5이므로 한 사람당 5개"라는 과정을 보여주며 답합니다.

Few-Shot CoT 예시 — 수학 문제

다음 문제를 단계별로 풀어 주세요.

문제: 빵 한 개의 가격이 1,200원입니다. 빵 5개를 사면 얼마인가요?
풀이:
1단계: 빵 한 개 가격 = 1,200원
2단계: 구매할 빵 개수 = 5개
3단계: 총 금액 = 1,200 × 5 = 6,000원
정답: 6,000원

문제: 책 한 권의 가격이 15,000원입니다. 10% 할인 쿠폰을 사용하면 얼마에 살 수 있나요?
풀이:
1단계: 책의 정가 = 15,000원
2단계: 할인율 = 10%
3단계: 할인 금액 = 15,000 × 0.1 = 1,500원
4단계: 최종 가격 = 15,000 - 1,500 = 13,500원
정답: 13,500원

11.4 Tree-of-Thought (ToT) 프롬프팅

Tree-of-Thought(ToT) 프롬프팅은 CoT를 한 단계 더 발전시킨 기법입니다. 하나의 사고 경로(Chain)가 아니라 여러 개의 가능한 경로(Tree)를 동시에 탐색하고, 그 중 가장 좋은 것을 선택합니다.

나무(Tree)처럼 여러 가지(Branch)로 뻗어나가며 생각하는 방식입니다.

11.5 Few-Shot + CoT 결합 기법

Few-Shot + CoT 결합은 두 기법의 장점을 합친 강력한 방식입니다. 예시를 제공(Few-Shot)하되, 각 예시에 단계별 사고 과정(CoT)까지 포함합니다.

3단계: 전체 합계 = 3,600 + 7,500 = 11,100원

정답: 10,000원으로는 부족하며, 1,100원이 더 필요합니다.

Self-Consistency (자기 일관성)

Self-Consistency는 동일한 문제에 대해 AI에게 여러 번 답하게 한 뒤, 가장 많이 나온 답을 최종 답으로 채택하는 기법입니다.

ReAct (Reasoning + Acting)

ReAct는 추론(Reasoning)과 행동(Acting)을 번갈아 수행하는 기법입니다. AI가 생각하고(Thought), 행동하고(Action), 결과를 관찰(Observation)하는 과정을 반복합니다.

주로 외부 도구(검색, 계산기, API 등)와 연동된 AI 에이전트에서 사용됩니다.

프롬프트 예시

다음 질문에 답하기 위해 생각-행동-관찰 과정을 반복해 주세요.

질문: 서울의 현재 인구는 도쿄 인구의 몇 퍼센트인가요?

생각 1: 서울과 도쿄의 인구를 각각 알아야 한다.
행동 1: 서울 인구 검색
관찰 1: 약 940만 명

생각 2: 이제 도쿄 인구를 알아야 한다.
행동 2: 도쿄 인구 검색
관찰 2: 약 1,400만 명

생각 3: 비율을 계산한다.
행동 3: 940 ÷ 1,400 × 100 = 67.1%
결론: 서울의 인구는 도쿄 인구의 약 67%입니다.

Prompt Chaining은 복잡한 작업을 여러 개의 작은 프롬프트로 쪼개어, 앞 단계의 출력을 다음 단계의 입력으로 연결하는 기법입니다.

11.7 2025년 최신 LLM 심화 활용 기법

앞서 살펴본 기법들이 "프롬프트를 어떻게 쓰는가"에 초점을 맞췄다면, 이 절에서는 최신 LLM이 제공하는 모델·API 차원의 심화 기능을 다룹니다. 같은 모델이라도 이 기능들을 활용하면 정확도, 비용, 안정성 면에서 큰 차이를 만들 수 있습니다.

📌 왜 이 절이 필요한가: 2024~2025년 사이 GPT-5, Claude 4.5/Opus 4.7, Gemini 2.5 같은 최신 모델은 단순한 텍스트 입력·출력을 넘어 확장 사고, 캐싱, 구조화 출력, 도구 호출, 외부 컨텍스트 연결 등 5가지 핵심 기능을 보편적으로 지원합니다. 이 기능들을 모르면 최신 모델을 절반밖에 활용하지 못합니다.

Extended Thinking (확장 사고)

Extended Thinking은 모델이 응답을 생성하기 전, 별도의 "사고(thinking)" 토큰 공간에서 충분히 추론한 뒤 최종 답을 내놓는 기능입니다. Claude 4.5/Opus 4.7의 thinking 파라미터, OpenAI o-series의 reasoning_effort 등이 대표적입니다.

  • 언제 효과적인가: 수학·논리·코드 디버깅·복잡한 의사결정처럼 단계적 추론이 필요한 작업
  • CoT와의 차이: CoT는 프롬프트로 "생각하라"고 유도하는 기법이지만, Extended Thinking은 모델이 내부적으로 수천~수만 토큰의 추론 공간을 별도로 할당받습니다. 사용자에게는 정제된 답만 보여지거나 사고 과정이 함께 공개됩니다.
  • 비용 주의: 사고 토큰도 과금됩니다. 단순 작업에는 끄고, 복잡 작업에만 켜는 것이 비용 효율적입니다.
# Anthropic Claude — Extended Thinking 예시
response = client.messages.create(
    model="claude-sonnet-4-5",
    max_tokens=4096,
    thinking={"type": "enabled", "budget_tokens": 8000},
    messages=[{"role": "user", "content": "복잡한 수학 문제를 풀어주세요..."}],
)

Prompt Caching (프롬프트 캐싱)

Prompt Caching은 동일한 시스템 프롬프트나 대용량 컨텍스트를 여러 번 호출할 때, 모델 측에서 토큰화·임베딩 결과를 캐싱하여 비용과 지연을 크게 줄이는 기능입니다.

  • 비용 절감 효과: 캐시 적중 부분은 일반 입력 토큰의 약 10% 가격으로 청구 (OpenAI/Anthropic 기준, 모델별 상이)
  • 지연 단축: 첫 응답 시간(Time to First Token)이 절반 이하로 단축되는 경우가 많음
  • 활용 사례: 챗봇의 긴 시스템 프롬프트, 장문 문서를 반복 참조하는 RAG, 동일 코드베이스에 대한 연속 질문
# Anthropic — cache_control로 캐싱 영역 지정
messages=[{
    "role": "user",
    "content": [
        {"type": "text", "text": "긴 문서 전체...",
         "cache_control": {"type": "ephemeral"}},
        {"type": "text", "text": "이 문서에서 ~를 찾아주세요"},
    ],
}]

Structured Output (구조화 출력)

Structured Output은 모델 응답이 반드시 지정된 JSON 스키마에 부합하도록 강제하는 기능입니다. OpenAI의 response_format={"type": "json_schema", ...}, Anthropic Tool Use를 활용한 JSON 강제, Gemini의 responseSchema 등이 있습니다.

  • 왜 필요한가: 프롬프트로 "JSON으로 답해주세요"라고 부탁하면 가끔 형식이 깨집니다. Structured Output은 모델 디코딩 단계에서 스키마를 강제하므로 100% 파싱 가능
  • 활용 사례: 폼 자동 채우기, 데이터 추출 파이프라인, 도구 호출 인자 생성
# OpenAI — JSON Schema 강제
schema = {
    "type": "object",
    "properties": {
        "name": {"type": "string"},
        "age": {"type": "integer"},
        "skills": {"type": "array", "items": {"type": "string"}},
    },
    "required": ["name", "age", "skills"],
}
response = client.responses.create(
    model="gpt-5",
    input=[{"role": "user", "content": "이력서에서 이름·나이·기술을 추출하세요..."}],
    response_format={"type": "json_schema", "json_schema": {"name": "Profile", "schema": schema}},
)

Tool Use (도구 호출)

Tool Use(또는 Function Calling)는 LLM이 외부 함수·API·DB를 호출할 수 있도록 하는 기능입니다. 사용자가 도구 명세(이름·설명·인자 스키마)를 제공하면, 모델은 필요 시 도구 호출 JSON을 출력합니다. 애플리케이션이 그 도구를 실행한 결과를 다시 모델에 전달하면, 모델이 최종 답변을 생성합니다.

  • 활용 사례: 실시간 검색, 데이터베이스 질의, 계산기, 캘린더·이메일 자동화, 코드 실행
  • 앞서 본 ReAct와의 관계: ReAct는 "생각·행동·관찰"이라는 사고 패턴이고, Tool Use는 이를 모델·API 레벨에서 지원하는 공식 메커니즘입니다.
  • 상세 학습: Chapter 16에서 OpenAI Function Calling을 코드와 함께 본격적으로 다룹니다.

MCP (Model Context Protocol)

MCP(Model Context Protocol)는 2024년 Anthropic이 제안하고 2025년에 OpenAI·Google·주요 IDE 진영이 채택한 AI 에이전트와 외부 도구·데이터를 연결하는 표준 프로토콜입니다. "AI 시대의 USB-C"라고도 비유됩니다.

  • 왜 필요한가: 각 도구를 모델마다 별도로 통합하면 N×M 조합 문제가 발생합니다. MCP는 도구 제공자와 모델 호출자가 모두 동일한 규격을 따르도록 표준화합니다.
  • MCP 서버: 도구·데이터·프롬프트를 노출하는 측 (예: GitHub MCP, PostgreSQL MCP, Slack MCP, Linear MCP)
  • MCP 클라이언트: Claude Desktop, Cursor, VS Code 등 LLM 애플리케이션
  • 개인 사용자도 활용 가능: Claude Desktop에 MCP 서버를 등록하면 로컬 파일·DB·API를 Claude가 직접 다룰 수 있습니다.
