크론 스케줄링의 구조

Hermes Agent의 크론 기능은 대화 중에 자동화 작업을 등록하고, 정해진 시간에 에이전트가 자동으로 실행하는 기능입니다.

자연어 파서는 없습니다

크론 시스템에 별도의 NLP 자연어 파서가 내장되어 있는 것이 아닙니다. LLM이 사용자의 자연어를 해석하여 parse_schedule() 함수가 받아들이는 구조화된 형식으로 변환합니다. 즉, "매일 아침 9시"라고 말하면 LLM이 이를 0 9 * * *으로 변환하여 크론 작업을 등록합니다.

스케줄 형식

parse_schedule() 함수가 받아들이는 형식은 다음 네 가지입니다.

형식 예시 설명
기간 문자열 30m, 2h, 1d 지금부터 지정 시간 뒤 1회 실행
인터벌 문자열 every 30m, every 2h 지정 간격으로 반복
크론 표현식 0 9 * * * 표준 5필드 cron
ISO 타임스탬프 2024-01-15T09:00:00 특정 시각 1회 실행

사용자가 "매주 월요일 오전 10시"라고 말하면, LLM이 이를 0 10 * * 1 크론 표현식으로 변환하여 등록합니다.

크론 작업 등록

대화 중에 에이전트에게 자동화 작업을 요청합니다.

> 매일 아침 9시에 디스크 사용량을 확인해서 80% 이상이면 알려줘

에이전트가 cronjob 도구를 사용하여 크론 작업을 등록합니다.

다양한 스케줄 표현이 가능합니다.

> 매주 월요일 오전 10시에 Git 저장소의 미병합 브랜치를 정리해줘
> 매 시간마다 서버 응답 시간을 체크해줘
> 매월 1일에 지난 달 작업 통계를 정리해줘
> 평일 오후 6시에 오늘 커밋한 내용을 요약해줘

크론 실행 조건

크론 작업이 실행되려면 게이트웨이가 실행 중이어야 합니다.

hermes gateway    # 게이트웨이 실행 중이면 크론도 자동 실행

게이트웨이 없이 수동으로 크론 틱을 트리거하려면 다음 명령을 사용합니다.

hermes cron tick

정해진 시각에 어떻게 실행될까

이 책은 가급적 내부 구현을 깊이 다루지 않지만, 크론은 한 가지를 알아 두면 운영이 한결 편해집니다.

Hermes의 크론은 운영체제의 crontab이나 launchd를 쓰지 않습니다. 게이트웨이 프로세스 안에서 도는 백그라운드 스레드가 60초마다 한 번씩 등록된 작업 목록을 훑어 보고, 실행할 때가 된 작업을 즉시 실행합니다. 앞서 본 hermes cron tick 명령은 이 점검을 수동으로 한 번 더 돌리는 것으로, 게이트웨이가 자동으로 돌고 있을 때는 쓸 일이 없습니다.

여기서 두 가지 실용적인 결과가 따라옵니다.

  • 해상도가 1분: 크론 표현식의 분 단위까지가 한계입니다. "30초마다" 같은 스케줄은 지원하지 않습니다.
  • 게이트웨이가 떠 있어야 작동: 게이트웨이가 꺼져 있으면 누구도 시간을 보고 있지 않으므로 정해진 시각이 와도 작업이 돌지 않습니다. 9장에서 hermes gateway install(사용자 서비스로 등록), 리눅스 서버라면 --system(부팅 시 자동 기동)을 권장한 이유가 여기에 있습니다.

같은 점검이 동시에 두 번 도는 일도 막혀 있습니다. 게이트웨이의 점검 스레드와 수동으로 친 hermes cron tick이 우연히 겹치더라도 한 번에 하나만 진행되므로, 같은 시각에 작업이 두 번 실행되는 일은 없습니다.

작업 격리

각 크론 작업은 격리된 AIAgent 세션에서 실행됩니다.

  • 작업 간 컨텍스트가 공유되지 않습니다
  • 이전 크론 실행의 메모리가 다음 실행에 전달되지 않습니다
  • 반복 방지: 크론 실행 중에는 cronjob 도구 세트가 비활성화됩니다. 크론 작업이 또 다른 크론 작업을 등록하는 재귀를 방지하는 안전장치입니다.

프로젝트 디렉터리에서 실행: workdir

기본적으로 크론 작업은 어떤 저장소와도 분리된 채 실행됩니다 — AGENTS.md·CLAUDE.md·.cursorrules가 로드되지 않고, 터미널·파일·코드 실행 도구의 작업 디렉터리는 게이트웨이가 시작된 위치 그대로입니다. 특정 프로젝트 폴더 안에서 작동하길 원하면 workdir을 지정합니다.

cronjob(
    action="create",
    schedule="매일 오전 9시",
    workdir="/home/me/projects/acme",
    prompt="이 프로젝트의 열린 PR을 점검해 #eng 채널로 요약을 보내줘",
)

workdir이 설정되면:

  • 해당 디렉터리의 AGENTS.md·CLAUDE.md·.cursorrules가 시스템 프롬프트에 주입됩니다(인터랙티브 CLI와 같은 탐색 순서)
  • terminal, read_file, write_file, patch, search_files, execute_code 모두 TERMINAL_CWD가 그 디렉터리로 설정된 채 실행됩니다
  • 반드시 절대 경로여야 하며, 존재하는 디렉터리여야 합니다 — 상대 경로나 없는 디렉터리는 등록·수정 시점에 거부됩니다
  • 편집 시 빈 문자열(workdir="")로 클리어하면 기본 작동으로 복귀합니다

workdir이 설정된 작업은 같은 틱에서 순차로 실행됩니다(병렬 풀에 들어가지 않음). TERMINAL_CWD가 프로세스 전역이라 두 workdir 작업이 동시에 돌면 서로의 cwd를 덮어쓰기 때문입니다. workdir이 없는 작업은 종전대로 병렬 실행됩니다.

작업 체이닝: context_from

다른 크론 작업의 가장 최근 성공 출력을 입력으로 받아오는 기능입니다. 작업 이름(또는 ID)을 context_from에 나열합니다.

cronjob(action="create", name="daily-digest",
        schedule="매일 오전 7시",
        context_from=["ai-news-fetch", "github-prs-fetch"],
        prompt="위 출력을 활용해 일일 다이제스트를 작성해줘.")

지정한 작업들의 최근 완료 출력이 프롬프트 위쪽에 컨텍스트로 주입됩니다. 주의: 같은 틱에서 같이 도는 상위 작업의 결과를 기다리지 않습니다 — 그 시점에 저장된 가장 최근 출력만 읽습니다. 따라서 체인을 의도한다면 상위 작업이 먼저 끝나도록 스케줄을 어긋나게 잡아야 합니다.

[SILENT] 마커

크론 작업의 응답이 [SILENT]로 시작하면 결과 전달이 억제됩니다.

이 기능은 "이상이 있을 때만 알려줘" 패턴에 유용합니다. 프롬프트에 다음과 같이 지시하면 됩니다.

디스크 사용량을 확인하세요. 80% 이하이면 [SILENT]로 시작하는 응답을 작성하세요.
80%를 초과하면 경고 메시지를 작성하세요.

정상 상태에서는 알림이 오지 않고, 문제가 발생했을 때만 메시지를 받게 됩니다.

결과 전달 옵션

크론 작업의 결과를 어디로 보낼지 deliver 옵션으로 지정할 수 있습니다.

옵션 설명
local 로컬 파일에만 저장
origin 작업을 등록한 플랫폼으로 전달
telegram Telegram 홈 채널로 전달
discord Discord 홈 채널로 전달
signal Signal로 전달
sms SMS로 전달
platform:chat_id 특정 플랫폼의 특정 채팅으로 전달

기본값

deliver를 지정하지 않으면 다음 규칙으로 자동 결정됩니다.

  • 텔레그램·디스코드 등 게이트웨이 채팅에서 잡을 등록한 경우 → origin. 잡을 등록할 때의 채팅 위치(플랫폼·채팅 ID)가 잡에 함께 저장되어 있다가 결과 회신 때 사용됩니다.
  • CLI 대화(hermes)에서 등록한 경우 → local. 외부 채널로는 알림이 가지 않고 로컬 파일에만 결과가 쌓입니다.

따라서 CLI에서 등록한 잡의 결과를 외부 채널로 받고 싶다면 명시해야 합니다. 자연어로 말해도 되며, 에이전트가 cronjob 도구 호출에 옵션을 끼워 넣습니다.

> 매일 아침 9시에 디스크 사용량 점검해서 텔레그램으로 보내줘

홈 채널 지정

telegram·discord·signal·sms로 전달하려면 해당 플랫폼에서 미리 홈 채널을 지정해 둬야 합니다.

> /sethome

이 명령을 실행한 채널이 크론 결과를 받는 "홈 채널"이 됩니다. 9장에서 다룬 메시징 게이트웨이가 떠 있어야 함은 물론입니다.

메시징 게이트웨이와 결합하면, 아침에 출근하면 Telegram에 어젯밤 서버 상태 리포트가 와 있는 식의 운영이 가능해집니다.

[SILENT]와의 관계

앞에서 본 [SILENT] 마커는 deliver와 독립된 레이어입니다. deliver가 무엇이든 응답이 [SILENT]로 시작하면 전달이 건너뜁니다. "이상이 있을 때만 알려달라" 패턴은 deliver="telegram"(또는 origin)으로 받을 채널을 지정하고 프롬프트에 [SILENT] 분기를 둠으로써 만듭니다.

놓친 작업 처리

반복 작업의 예정 시간에 게이트웨이가 꺼져 있었다면, 다시 시작했을 때 놓친 작업을 한꺼번에 몰아서 실행하지 않습니다. 다만 짧게 놓친 경우에는 한 번만 따라잡기(catch-up) 실행을 합니다. 따라잡기를 허용하는 유예 구간은 스케줄 주기의 절반(최소 2분, 최대 2시간)이며, 이 구간을 넘기면 마지막 실행 시각을 갱신하고 다음 예정 시각부터 정상 실행됩니다(fast-forward).

예를 들어, 하루 1회 작업은 최대 2시간까지 늦더라도 재시작 시 1회 따라잡기 실행됩니다. 반면 매시간 작업이 3시간 동안 놓쳤다면 3번 몰아 실행하지 않고, 유예 구간(30분)을 넘긴 만큼 다음 정시에 1회만 실행합니다.

프롬프트 보안

크론 작업의 프롬프트는 등록 시 보안 스캐닝을 거칩니다.

  • 인젝션 탐지: 시스템 프롬프트 조작 시도 감지
  • 데이터 유출 탐지: 민감한 데이터를 외부로 전송하는 패턴 감지
  • 비가시 유니코드: 보이지 않는 유니코드 문자(zero-width space 등) 탐지

이 검사는 악의적인 프롬프트가 크론 작업으로 등록되는 것을 방지합니다.

크론 작업 관리

등록된 크론 작업을 확인하고 관리합니다.

> 등록된 크론 작업 목록을 보여줘
> 디스크 체크 크론을 삭제해줘
> 일일 리포트 크론의 실행 시간을 오전 8시로 변경해줘
> 모든 크론 작업을 일시 정지해줘

활용 사례

시스템 운영

  • 일일 리포트: 매일 아침 시스템 상태(CPU, 메모리, 디스크) 요약
  • 야간 백업 확인: 백업 스크립트 실행 후 성공 여부 확인 및 보고
  • 로그 분석: 매일 에러 로그를 분석하고 심각도별 분류

개발 워크플로

  • 코드 품질: 주기적으로 린트, 테스트 커버리지, 의존성 취약점 체크
  • 브랜치 정리: 매주 병합 완료된 브랜치를 목록으로 정리
  • 의존성 업데이트: 매주 업데이트 가능한 패키지 확인 및 보고

정보 수집

  • 뉴스 브리핑: 매일 특정 주제의 최신 정보 수집 및 요약
  • 경쟁사 모니터링: 정기적으로 특정 웹사이트 변화 체크
  • 기술 트렌드: 매주 GitHub 트렌딩 저장소 분석

비용 고려사항

크론 작업은 매 실행마다 LLM을 호출하므로, 비용을 고려해야 합니다.

  • 로컬 LLM: 전기 비용만 발생하므로 빈번한 스케줄도 부담이 적습니다
  • 클라우드 API: 실행 빈도와 작업 복잡도에 따라 토큰 비용이 발생합니다
  • 권장: 처음에는 일 1~2회 정도로 시작하고, 필요에 따라 늘려가는 것이 좋습니다

잡별 모델 지정

크론 잡은 메인 세션과 다른 모델·프로바이더를 쓰도록 설정할 수 있습니다. 평소 대화는 클라우드 프론티어 모델로 하면서, 매일 도는 단순 요약 잡은 로컬 모델로 돌리는 식의 분리가 가능합니다.

스케줄러는 잡 실행 시 다음 순서로 모델을 결정합니다.

  1. 잡에 저장된 model·provider(있으면 우선)
  2. 환경 변수 HERMES_MODEL
  3. config.yaml의 model.default

설정 경로는 두 가지입니다.

  • 자연어 등록 시 함께 지정: 잡을 등록할 때 모델·프로바이더를 함께 일러두면, 에이전트가 cronjob 도구 호출에 반영합니다.

    > 매일 아침 9시에 GitHub 트렌딩을 요약해줘. 모델은 로컬 qwen3:14b로 돌려.

  • ~/.hermes/cron/jobs.json 직접 편집: 잡 객체의 "model"·"provider"·"base_url" 키를 추가하거나 수정합니다.

프로바이더 고정 방식

자연어 등록에서 모델만 지정하고 프로바이더를 생략하면, 잡 생성 시점의 메인 프로바이더가 잡에 함께 저장됩니다. 이후 hermes model로 메인 프로바이더를 바꿔도 잡은 옛 프로바이더로 계속 실행됩니다. 메인 프로바이더 변경에 자동으로 따르게 하려면 jobs.json에서 해당 잡의 provider 필드를 null로 비워 둡니다.
